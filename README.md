# HotelFlow — Hotel Management App

A Java Swing desktop application with SQLite. It does not use Spring. Requires Java 17 or later.

## Run the app

1. Install JDK 17+ and Maven 3.8+.
2. Open a terminal in the project folder and run `mvn clean package`.
3. Start the app with `java -jar target/hotel-manager-1.0.0.jar` (or run `mvn exec:java`).

### Run without Maven (Windows)

The app still needs its third-party libraries even when you build without Maven. Download these JAR files from Maven Central and place them in a `lib` folder in the project root:

- `sqlite-jdbc-3.47.1.0.jar`
- `pdfbox-3.0.4.jar`
- `pdfbox-io-3.0.4.jar`
- `fontbox-3.0.4.jar`
- `commons-logging-1.3.4.jar`

Then double-click `run.bat`, or open PowerShell in the project root and run:

```powershell
New-Item -ItemType Directory -Force out
javac -encoding UTF-8 -cp "lib/*" -d out src\main\java\vn\hotel\HotelApp.java
java -cp "out;lib/*" vn.hotel.HotelApp
```

### Run without Maven (Linux / macOS)

```bash
mkdir -p out
javac -encoding UTF-8 -cp "lib/*" -d out src/main/java/vn/hotel/HotelApp.java
java -cp "out:lib/*" vn.hotel.HotelApp
```

Do not run `java HotelApp.java` from inside `src\main\java\vn\hotel`; that command does not include the dependency JARs.

## Features

- Sign-in and role-based access for administrators, receptionists, and customers.
- Sign-up for new customers: from the Sign in screen, click "Sign up", enter full name, username, password (at least 6 characters), confirm password and optional phone. New accounts are always customers; staff accounts are still created only by an Admin in Staff management, so a visitor cannot give themselves admin or receptionist rights. After sign-up, the username is filled in on the Sign in screen — just enter the password and sign in. Sign-up does not reveal whether a username is already taken (see "Privacy and security" below), usernames are checked without distinguishing upper/lower case, and the Sign in screen no longer pre-fills any account or shows demo passwords.
- Privacy by role on the Dashboard: a customer sees only their own recent bookings and their own booking count — never other guests' bookings, other guests' phone numbers, or hotel revenue. Staff see all recent bookings and revenue, as before.
- Passwords are stored as SHA-256 hashes with a random salt (pure JDK, no new library). Accounts created before this change still sign in with their old password, and are automatically converted to a hash on their first successful sign-in, so no existing account breaks.
- Room management, rates, room types, and availability status.
- Bookings, check-in/check-out, and laundry or minibar charges.
- Automatic invoice calculation by nights and services; export as TXT or PDF.
- Revenue reports by day, month, or year, with a bar chart.
- Staff/customer account creation, booking history, room search, and customer reviews.
- Cleaning queue: rooms marked Cleaning after check-out can be marked as cleaned in one click to become Available again (sidebar: Housekeeping).
- Booking search and filter: find bookings by guest name or room number, and filter by Reserved / Occupied / Checked out / Cancelled / No-show (Bookings & stays).
- Cancel and extend a stay: cancel a Reserved booking, or extend a Reserved/Occupied booking by extra nights with an overlap check (Bookings & stays).
- Invoice discount: add a 0–100% discount together with laundry/minibar charges; the invoice and check-out total show subtotal, discount, and total due.
- Export and backup: export bookings or rooms as CSV for Excel / Google Sheets, and back up `hotel.db` to a file of your choice (sidebar: Export & backup, for Admin and Receptionist).
- Advanced room search for customers: by check-in/check-out dates, number of guests, price range, room type, minimum capacity, amenities, and real availability for those dates (not just the room's current status). Room details show description, base rate, capacity, amenities, image path, hotel check-in/check-out times and the cancellation policy.
- Booking with a full price breakdown before confirmation: room charge per night (seasonal/weekend rules applied), promotion discount, tax, and total, plus guest count, occupant names and special requests. Every booking gets a code like `HF-000123`.
- Payments and receipts: record cash/card/transfer payments as Deposit, Partial or Full, track payment status (Unpaid / Deposit / Partial / Paid / Refunded), and save a TXT receipt. Check-out collects the remaining balance (or refunds an overpayment) before closing the stay.
- Customer booking management: filter upcoming vs history, view full booking details, change dates/guest info when the policy allows (dates only for Reserved bookings before check-in), cancel with a policy-based refund that is recorded as a Refund transaction.
- Service flow done properly: Admin sets up the service catalog and prices; customers request services (Pending, NOT charged); Receptionist confirms a request only after the service was provided, and only then is it added to the bill. Manual services for already-provided work use the same confirmed charge.
- Reviews after a completed stay: separate room and service ratings, a comment, staff replies, and Admin moderation (hide/show) with average ratings.
- My account: update full name, phone, email and notification preference, and change password only after verifying the current password.
- Support requests: customers send help requests about a booking (or general), staff reply and change status (Open / In progress / Resolved).
- Shift tools for Receptionist: Shift dashboard (arrivals, in-house, departures, vacant and to-handle rooms), in-house guest management (extend, change room, notes, early check-out), and Shift handover (today's summary, pending items, handover notes).
- Housekeeping and maintenance tasks: create, start and complete cleaning/maintenance tasks with an assignee, and set the room back to Available on completion.
- Admin pricing and inventory: per-night price rules (all rooms / one type / one room, seasonal and weekend-only), promotion codes, and closing/opening sale by room type or per room.
- Admin customers, staff and system: customer profiles with booking history and care notes; staff role changes, account locking and shift assignment (with fixed permission limits, e.g. Receptionist discount max 20%, no payment voiding); detailed Reports (revenue, occupancy, ADR, cancellation/no-show rates, service revenue, payment methods, revenue by room type); System configuration (hotel details, check-in/out times, cancellation policy, currency, tax, deposit) and an audit log of important actions.
- Room types as a real master list (Admin only): create, edit, activate/deactivate and delete room types with a default base price, capacity and amenities. New rooms pick a type from this list (or type a new one, which is then added to the list automatically). Editing a type changes the defaults for NEW rooms only — rooms already created keep their own price/capacity unless you edit the room itself, so existing bookings never change price by surprise. Deleting a type that rooms still use is blocked.
- Room photos stored inside the database: in Add/Edit room, Admin can “Choose image file…” (PNG/JPG/GIF, up to 5 MB) and the image is saved as a BLOB in `hotel.db`, so it travels with the backup file. Room details show the stored photo (scaled) together with the optional path/URL field, which is kept for external links.
- Notifications for every important event: booking confirmed, payment recorded, service confirmed or declined, support reply, review reply, check-in, check-out, and shift assignments are saved in a Notifications inbox (menu “Notifications” for all roles) with Mark as read / Mark all as read. Staff do not need a separate chat to know what happened to a booking.
- Email via the user's own mail app (pure Java, no SMTP password stored): in My bookings, “Email confirmation” opens the default mail app (Outlook, Thunderbird, Mail, …) with the guest's email, subject and full booking confirmation prefilled; in Invoices, “Email invoice” does the same with the invoice text. If no mail app is available, the email text is saved as a file instead, so nothing is lost. Automatic background email sending is NOT included yet, because it needs the hotel's own SMTP server and account — see “Những gì chưa có” below.
- Staff can now fully edit a booking (Bookings & stays → Edit booking): change guest (for a checked-in booking, only Admin), room, dates, guest count, occupants, special requests and stay notes, with the same availability check as a new booking and with room-status handling for checked-in stays (old room → Cleaning, new room → Occupied). The new room charge estimate is shown before confirming.
- Customer Dashboard shows the next stay at the top (“Next stay: HF-… · Room … · dates · nights”), and My bookings can export the invoice as a TXT file after check-out (before check-out it shows the details and explains that the invoice file is available after check-out).
- Reports export button is now honestly labelled “Save report as text” (it saves the report text, not a CSV).
- Sidebar no longer hides the Administration menu: the old sidebar set its own height to 0, so the scroll pane did not know the menu was taller than the window and the bottom items (Prices & inventory, Room types, …) were clipped with no scrollbar. The sidebar is now compact (shorter buttons and spacing, about 300 px saved for an Admin) and its scrollbar is always visible, so you can scroll down to Administration on any window size. On a short window, scroll the dark left menu with the mouse wheel — the scrollbar on its right edge shows there is more below.
- A booked room no longer looks free: Room management now shows a derived “Status” and an “Upcoming booking” column. If a room is booked for tonight (a Reserved booking with check-in today and check-out after today) but the guest has not checked in yet, Status shows **Reserved** instead of Available, and Upcoming booking shows the code, guest and dates (e.g. HF-000001 · Quang Minh · 2026-10-28 to 2026-10-30). The underlying room status in the database is still Available until check-in — only the display changes, so check-in, availability checks and pricing are untouched. Shift dashboard “VACANT ROOMS” now also excludes rooms booked for tonight, so it counts rooms that are really sellable tonight.
- Demo data on first run (only for empty tables, never overwriting real data): when a table is empty, the app seeds 2–3 ready-to-use rows so every menu can be tried immediately — see “Dữ liệu mẫu có sẵn” below. If you already have real bookings (like the Quang Minh booking in your screenshots), demo bookings are NOT added on top of them; only the tables that are still empty in your database (for example Price rules and Promotions, which were empty in your screenshot) get demo rows.
- All of the above is still pure Java (JDK only for new code, no Spring, no new library). Existing project libraries (SQLite JDBC, PDFBox) are unchanged.

## Dữ liệu lưu ở đâu? (hotel.db)

Tất cả dữ liệu của app nằm trong **1 file duy nhất: `hotel.db` (SQLite)**, không có máy chủ, không có cloud, không đồng bộ lên GitHub.

- **File nằm ở đâu:** code dùng đường dẫn tương đối `hotel.db`, và `run.bat` luôn chuyển về thư mục chứa chính nó (`cd /d "%~dp0"`) trước khi chạy. Vì vậy trên Windows, file nằm **ngay trong thư mục chứa `run.bat`** — ví dụ `C:\...\hoteljava\hotel.db`, nằm cạnh `src\`, `lib\`, `out\`, `README.md`. Bạn mở thư mục đó trong File Explorer là thấy file `hotel.db`.
- **Trong file có gì:** mọi bảng — tài khoản, phòng, loại phòng, booking, thanh toán, dịch vụ, yêu cầu dịch vụ, đánh giá, hỗ trợ, ca trực, ghi chú bàn giao, task buồng phòng, price rule, khuyến mãi, cấu hình, nhật ký thao tác, thông báo — và cả ảnh phòng (lưu dạng BLOB trong cùng file). Một file là đủ để mang cả khách sạn đi.
- **Đơn của Quang Minh ở đâu:** đơn HF-000001 phòng 102 trong ảnh của bạn chỉ nằm trong file `hotel.db` trên máy Windows của bạn, mình không nhìn thấy và không lấy được nó. GitHub chỉ chứa code và README, không chứa đơn đặt phòng của bạn.
- **Sao lưu và khôi phục:** vào menu **Export & backup** để copy `hotel.db` ra một file bạn chọn (ví dụ lưu lên USB, ổ D, hoặc Desktop). Muốn khôi phục: **tắt app hoàn toàn**, ghi đè file `hotel.db` trong thư mục app bằng file sao lưu, rồi mở app lại. Đừng ghi đè khi app đang chạy.
- **Cẩn thận với git:** file `hotel.db` đã có sẵn trong repo từ bản gốc nên git vẫn đang theo dõi nó. Các commit của mình **không bao giờ đụng tới `hotel.db`**, vì vậy khi bạn `git pull` để lấy code mới, git sẽ giữ nguyên file `hotel.db` đã sửa trên máy bạn (vì phía remote không thay đổi file đó). Tuyệt đối **đừng chạy `git add hotel.db` hay commit file này** — repo có thể là public, commit lên là lộ tên/SĐT khách. Trước mỗi lần pull, cứ copy `hotel.db` ra ngoài thư mục repo để dự phòng là an toàn nhất. File `.gitignore` mới thêm vào chỉ chặn `out/` và các file sao lưu, nó **không** tự gỡ theo dõi `hotel.db` cũ — nếu bạn muốn gỡ hẳn file này khỏi git, báo mình, mình sẽ làm theo từng bước có sao lưu, vì làm ẩu có thể khiến lần pull sau báo lỗi hoặc xóa nhầm file trên máy bạn.
- **Bẫy thường gặp:** nếu bạn chạy app bằng IDE hoặc gõ lệnh `java` từ một thư mục khác (không qua `run.bat`), app sẽ tạo một file `hotel.db` mới **trong thư mục đó**, và bạn sẽ thấy app “trống trơn” dù file cũ vẫn còn. Lúc đó đừng nhập lại dữ liệu — hãy đóng app, chạy lại bằng `run.bat` trong thư mục repo là dữ liệu cũ hiện lại.

## Dữ liệu mẫu có sẵn (để thao tác ngay, chỉ seed khi bảng còn trống)

Mỗi mục dưới đây có sẵn 2–3 dòng khi bạn mở app sau khi cập nhật (nếu bảng đó trong máy bạn đang trống; bảng nào đã có dữ liệu thật thì giữ nguyên, không thêm demo chồng lên):

- **Prices & inventory:** 3 price rule — Standard cuối tuần 700.000/đêm, Deluxe mùa cao điểm 1.100.000/đêm, phòng 301 VIP giá mùa 1.900.000/đêm; 3 khuyến mãi — `SALE10` giảm 10% mọi phòng (đang bật), `WEEKEND15` giảm 15% phòng Standard (đang bật), `VIP20` giảm 20% phòng VIP (đang tắt, để bạn thử nút Activate / deactivate). Dùng `SALE10` khi đặt phòng thử là thấy giảm giá ngay.
- **Bookings & stays / Shift dashboard / Guests staying now:** 3 đơn — Quang Minh, phòng 102, nhận hôm nay → trả sau 2 ngày, trạng thái Reserved, đã đặt cọc 330.000 (dùng để thử Check-in và thấy phòng 102 hiện Reserved); Thu Ha, phòng 201, nhận hôm qua → trả ngày mai, trạng thái Occupied, đã trả một phần 900.000 (dùng để thử dịch vụ, gia hạn, đổi phòng, trả phòng); Sample customer, phòng 301, kỳ đã trả phòng cách đây 8–10 ngày, đã thanh toán đủ 3.200.000 (dùng để thử hóa đơn và đánh giá). Tài khoản demo: Quang Minh / Thu Ha, mật khẩu đều là `123456` (đổi sau khi thử xong nếu dùng thật).
- **Services & requests:** 1 yêu cầu Pending (Spa 60 phút cho đơn Thu Ha, để thử Confirm → cộng tiền / Decline → không tính tiền) và 1 dịch vụ đã Confirmed (Bữa sáng buffet x2 cho cùng đơn, đã nằm trong hóa đơn).
- **Payments / Invoices:** 3 giao dịch tương ứng 3 đơn trên — Deposit, Partial, Full — để thử xem, ghi thêm thanh toán, và xuất hóa đơn TXT/PDF cho đơn đã trả phòng.
- **Support:** 2 yêu cầu — 1 Open của Quang Minh (cần thêm gối/khăn, để thử trả lời) và 1 Resolved của Thu Ha (đã có câu trả lời mẫu).
- **Reviews & replies:** 2 đánh giá Approved — 1 của kỳ đã trả phòng (5 sao phòng, 4 sao dịch vụ, đã có trả lời mẫu) và 1 đánh giá chung (4 sao phòng, 5 sao dịch vụ, chưa trả lời, để thử Reply và Hide / show).
- **Housekeeping:** 2 task — Cleaning phòng 101 (Pending, để thử Start → Complete) và Maintenance phòng 302 (In progress, để thử Complete và đưa phòng về Available).
- **Staff / Shift handover:** 2 ca của Lễ tân (Morning hôm nay, Night ngày mai) và 2 ghi chú bàn giao mẫu, cộng 4 thông báo mẫu trong Notifications (xác nhận đơn, ghi thanh toán, xác nhận dịch vụ, phân ca).
- **Rooms / Room types / Service catalog / Customers:** đã có sẵn từ trước — 6 phòng, 3 loại phòng (Standard, Deluxe, VIP), 7 dịch vụ, và nay thêm 2 khách demo (Quang Minh, Thu Ha) nên trang Customers có 3 khách để xem hồ sơ và ghi chú chăm sóc.
- **Lưu ý về ngày demo:** ngày của các đơn demo được tính theo ngày bạn mở app lần đầu sau khi cập nhật (hôm nay, hôm qua, ngày mai…). Nếu vài ngày sau bạn mới mở lại, đơn “nhận hôm nay” sẽ thành đơn quá ngày — đó là dữ liệu demo, bạn cứ sửa ngày, hủy, hoặc dùng đơn đó để thử Mark no-show, đừng coi nó là đơn thật.

### 2. Receptionist (Lễ tân) — vận hành hằng ngày và ca trực

## Luồng dịch vụ và thanh toán — ai làm gì (đọc kỹ, vì đây là điểm dễ hiểu nhầm)

1. **Admin thiết lập:** tạo danh mục dịch vụ (tên, nhóm, mô tả, đơn giá, giờ phục vụ, trạng thái khả dụng) trong “Service catalog”, và thiết lập thuế/phí, % đặt cọc, chính sách hủy trong “System configuration”.
2. **Customer yêu cầu:** xem menu trong “Services”, chọn dịch vụ + số lượng + kỳ lưu trú đang check-in, xác nhận yêu cầu. Yêu cầu ở trạng thái **Pending** và **không** được cộng vào hóa đơn.
3. **Receptionist/Admin xác nhận:** trong “Services & requests”, chỉ bấm “Confirm” khi dịch vụ đã thực sự được cung cấp (ví dụ: giặt là đã trả đồ, bữa ăn đã phục vụ, xe đã đón). Lúc đó hệ thống mới tạo một dòng dịch vụ đã xác nhận và cộng đúng số tiền (đơn giá lúc yêu cầu × số lượng) vào hóa đơn của kỳ lưu trú đó. Nếu từ chối, yêu cầu thành Cancelled và không tính tiền.
4. **Ghi tay khi cần:** nếu khách không gửi yêu cầu qua app (ví dụ: gọi điện xuống lễ tân), Lễ tân ghi trực tiếp ở bảng dưới của “Services & requests” (chọn booking, chọn dịch vụ từ danh mục hoặc “Custom service”, nhập số lượng, xác nhận tổng tiền) — và cũng chỉ ghi khi dịch vụ đã cung cấp.
5. **Thanh toán:** khách hoặc Lễ tân ghi thanh toán trong “Payments” hoặc “My bookings → Pay” (tiền mặt/thẻ/chuyển khoản; đặt cọc/trả một phần/trả hết). Trạng thái thanh toán của đơn tự cập nhật theo tổng đã trả so với tổng tiền. Khi trả phòng, Lễ tân đối chiếu tổng tiền, đã trả và còn thiếu, thu phần còn thiếu (hoặc hoàn phần thừa) rồi mới chốt đơn thành Checked out và xuất hóa đơn.

## Quy tắc tính tiền, hủy và hoàn tiền (mặc định, Admin có thể đổi trong System configuration)

- **Tiền phòng:** cộng từng đêm, mỗi đêm áp giá theo rule (phòng cụ thể → loại phòng → chung; cuối tuần riêng) nếu có, không thì giá gốc của phòng. Đổi phòng giữa kỳ: tiền phòng tính lại theo phòng mới cho toàn bộ kỳ (hoặc từ ngày đổi, tùy thao tác đổi phòng trong app — app hiện chênh lệch trước khi xác nhận).
- **Dịch vụ:** chỉ dịch vụ đã xác nhận (catalog) + giặt ủi/minibar (mục cũ trong “Bookings & stays → Laundry / Minibar / Discount”) mới tính vào hóa đơn. Yêu cầu Pending không tính.
- **Giảm giá:** giảm % khuyến mãi (khi đặt phòng, theo mã) + giảm % do nhân viên áp (khi ở, trong “Laundry / Minibar / Discount”). Tổng % giảm tối đa 100%. Lễ tân áp giảm tối đa 20%, Admin tới 100%.
- **Thuế:** thuế = (tổng phụ − giảm giá) × thuế hệ thống. Mặc định thuế 0%, nên tổng tiền cũ (phòng + dịch vụ − giảm giá) vẫn giữ nguyên nếu Admin chưa đổi thuế. Tổng tiền = tổng phụ − giảm giá + thuế.
- **Đặt cọc:** mặc định 30% tổng tiền (chỉ là gợi ý số tiền khi chọn loại Deposit trong hộp thoại thanh toán, không tự trừ tiền).
- **Hủy và hoàn tiền (khách hủy đơn Reserved):** hủy trước ngày nhận phòng từ 2 ngày trở lên (số ngày hủy miễn phí, mặc định 2): hoàn 100% số đã trả. Hủy trong 1 ngày trước ngày nhận: hoàn 50% số đã trả. Hủy sau khi đã nhận phòng hoặc không đến (no-show): không hoàn, trừ khi Admin ghi hoàn riêng. Lễ tân phải dùng đúng số hoàn theo chính sách; Admin được điều chỉnh số hoàn khi hủy. Tiền hoàn được ghi thành giao dịch Refund và hiện trong chi tiết đơn.
- **Trạng thái đơn:** Reserved (đã đặt) → Occupied (đang ở, tức là đã check-in) → Checked out (đã trả) / Cancelled (đã hủy) / No-show (không đến). Phòng: Available (trống, đang bán) / Occupied (đang có khách) / Cleaning (cần dọn) / Maintenance (đang bảo trì) / Closed (khóa, không bán). Trạng thái thanh toán: Unpaid / Deposit / Partial / Paid / Refunded / Partially refunded.

## Những gì chưa có (nói thẳng, để không hiểu nhầm)

- **Chưa gửi email/SMS tự động nền, chưa kết nối cổng thanh toán online:** app đã có thông báo trong app và gửi email xác nhận/hóa đơn qua mail app của máy (xem Features), nhưng không tự gửi email/SMS nền và không trừ tiền thẻ thật; thanh toán vẫn là ghi nhận trong nội bộ (tiền mặt/thẻ/chuyển khoản do Lễ tân/khách ghi lại). - **Không có đặt phòng online đa chi nhánh, không có đồng bộ lịch với OTA, không có quản lý kho vật tư:** app là hệ thống 1 khách sạn, 1 database file `hotel.db`, chạy trên máy tính để bàn.

Passwords for new accounts (sign-up, Staff creation, and demo accounts on a fresh database) are stored as SHA-256 hashes with a random salt, using only the JDK. A database created before this change may still contain plain-text demo passwords; those accounts still sign in normally and are converted to a hash on their first successful sign-in. ## Privacy and security — what was fixed, and what still needs care

These fixes are all pure Java (JDK only, no Spring, no new library):

- **Sign-up no longer confirms whether a username exists.** Trying to register an existing username (in any upper/lower case) now shows only a generic message asking you to try signing in with it or choose a different username, creates no second account, and leaves the existing account's password untouched. This stops bulk username enumeration through the sign-up form. The Staff screen keeps a clear "already exists" message because an Admin there already sees the full user list.
- **The Sign in screen no longer leaks an account.** It used to pre-fill `admin` / `admin123` and print all demo passwords underneath, so anyone opening the app could click Sign in and become Admin without knowing anything. Now both fields start empty, no demo password is shown on screen, and demo accounts are documented only here in README for development. Before any real use, change or delete the demo accounts (`admin`, `le_tan`, `khach`) and do not leave their passwords in this file.
- **A customer can no longer see other guests' data on the Dashboard.** Before, every role saw all recent bookings and total revenue on the home page, so a newly signed-up customer could see other guests' names, rooms and dates, plus hotel revenue. Now a customer sees only their own recent bookings and their own booking count; revenue and other guests' bookings are staff-only. Customers still see only their own bookings in "My bookings", only available rooms in "Find a room", and no other user's phone number anywhere in their menus.
- **Passwords are masked where they are typed.** Staff account creation used a plain text field for the password; it now uses a password field (dots). Sign-up already used password fields. Sign-up failures no longer show raw database error text to an unauthenticated user; they show a generic "could not be created" message instead.
- **Usernames are case-insensitive for login and sign-up.** `ADMIN` cannot be registered to impersonate `admin`, and logging in as `ADMIN` with the right password signs in as `admin`. Login failures still give only the generic "incorrect" message, without saying whether the username or the password was wrong.
- **What is not fixed by this change:** usernames themselves are not secret in a hotel system (staff know guest names, and bookings show guest names to staff), so a determined person who already knows a username can still try to sign in as that user — the protection here is the password, the hash, and changing the demo passwords. File `hotel.db` itself must still be kept safe: anyone with the file and the app can try to sign in, and an Admin can see all users' names, usernames, roles and phone numbers in Staff management (that is the Admin's job, not a customer feature).
